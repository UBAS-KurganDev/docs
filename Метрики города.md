У меня есть сервис, который строит выгодные авиамаршруты и один из компонентов этой системы используют оценку каждого города по его туристической привлекательности для системы нужен scale от 0 до 100, как бы ты рекомендовал строить данную систему? Так как данных нужно много нужен автосбор такой метрики скриптом.

Для создания такой системы автоматического сбора туристической привлекательности городов (в шкале от 0 до 100) лучше всего применить подход **ранжированного агрегирования внешних сигналов** (composite index). Ни один изолированный источник не даст объективную картину, но комбинация открытых геоданных, поисковой активности и туристической инфраструктуры формирует надежный и масштабируемый пайплайн.

  

### 1. Архитектура метрики: из чего складывается балл (0–100)

Итоговый индекс города $S$ можно представить как взвешенную сумму нескольких нормализованных факторов:

  

$$S = w_1 \cdot P + w_2 \cdot A + w_3 \cdot I + w_4 \cdot C$$

Где компоненты отражают следующие аспекты:

  

- **$P$ (Popularity / Популярность):** Объём поискового интереса и упоминаний (Google Trends / Википедия).
    
      
    
- **$A$ (Attractions / Достопримечательности):** Плотность и качество точек притяжения (OpenStreetMap / Викигид).
    
      
    
- **$I$ (Infrastructure / Инфраструктура):** Доступность для путешественников — отели, транспорт, аэропорты (OpenStreetMap / агрегаторы).
    
      
    
- **$C$ (Culture & Diversity / Культурное разнообразие):** Наличие музеев, исторический статус, разнообразие категорий мест.
    
      
    

### 2. Источники данных для автосбора

Для автоматизации скрипта подойдут следующие бесплатные и открытые источники:

  

#### А. Википедия (Культурная значимость и важность)

- **Что собираем:** Количество языковых версий статьи о городе, длину статьи, количество просмотров страницы за год (через Pageviews API). Города с большими статьями на десятках языков — это мировые хабы (Рим, Париж), а небольшие региональные центры получат соразмерно меньший вес.
    
      
    
- **Инструмент:** `wikipedia-api` или официальный REST API Википедии.
    
      
    

#### Б. OpenStreetMap (OSM) — Плотность инфраструктуры и точек интереса (POI)

Через Overpass API можно делать запросы на подсчет объектов в радиусе города:

  

- **Туристические объекты:** `tourism=attraction`, `historic=*`, `amenity=arts_centre`, `museum`.
    
      
    
- **Инфраструктура:** `tourism=hotel`, `amenity=restaurant`, `amenity=cafe`.
    
      
    
- **Транспорт:** Наличие аэропортов (`aeroway=aerodrome`), ж/д станций (`railway=station`).
    
      
    
- **Инструмент:** Python-библиотека `osmnx` или прямые запросы к Overpass API.
    
      
    

#### В. Викигид (Wikivoyage)

- **Что собираем:** Списки достопримечательностей (разделы _See_, _Do_). Наличие подробного гайда по городу — сильный маркер того, что направление сформировано как туристическое.
    
      
    

### 3. Алгоритм работы скрипта (Пайплайн сбора)

Скрипт должен работать итеративно (например, раз в месяц или квартал для обновления кэша в БД):

  

1. **Список городов:** Берется база ваших аэропортов / городов (например, из базы маршрутов).
    
      
    
2. **Сбор сырых метрик (Worker):**
    
      
    - Запрос к OSM Overpass API: количество `attraction`, `museum`, `hotel`.
        
          
        
    - Запрос к Википедии: количество просмотров статьи о городе за последний год + количество межъязыковых ссылок.
        
          
        
3. **Нормализация (Min-Max scaling или Логарифмирование):**
    
      
    - Сырые данные имеют огромный разброс (условный Париж имеет миллионы просмотров, а уездный город — пару тысяч). Примените логарифмирование $\log(x + 1)$ к таким метрикам, чтобы сгладить выбросы.
        
          
        
    - Затем приведите значения каждого фактора к шкале от 0 до 1 с помощью Min-Max нормализации по всей базе городов.
        
          
        
4. **Расчет весов и итогового балла:**
    
      
    - Суммируйте нормализованные показатели с весами (например: OSM Attractions — 35%, Википедия/Популярность — 35%, Инфраструктура/Отели — 30%).
        
          
        
    - Умножьте на 100, чтобы получить итоговый диапазон.
        
          
        

### 4. Защита от «слепых зон» и ручная калибровка

- **Поправка на размер города:** Мегаполисы вроде Москвы или Токио будут доминировать по количеству объектов просто за счет масштаба, хотя для туриста маленький исторический городок (например, Брюгге или Сиде) может быть интереснее. Можно ввести _плотностной коэффициент_ (делим количество объектов на площадь города или количество жителей), но для авиабилетов чистая популярность и развитость инфраструктуры часто важнее, так как туда проще добраться.
    
      
    
- **Интеграция с вашими данными:** Если у вас уже есть статистика поисков пользователей или бронирований в системе, добавьте её как еще один мультипликатор ($w_5 \cdot \text{UserSearchDemand}$). Это сделает модель самообучающейся под вашу аудиторию.
    
      
    

### Рекомендация по реализации

Начните с MVP на Python:

  

1. Напишите скрипт, который берет топ-100 ключевых городов вашей маршрутной сети.
    
      
    
2. Подтяните для них данные из **OpenStreetMap** (через `osmnx`) и **Wikivoyage/Wikipedia**.
    
      
    
3. Закиньте сырые метрики в таблицу PostgreSQL, где подберите веса вручную «на глаз» (чтобы в топе логично оказались Париж, Рим, Стамбул, а внизу — промышленные моногорода).
    
      
    
4. Как только формула начнет давать адекватный порядок, оберните скриптовую логику в Airflow/Cron-задачу для автоматического обновления раз в сезон.
